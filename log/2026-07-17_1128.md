## What Was Accomplished

### 1. Municipality Name Cleaning — Complete Overhaul
The `municipio_name` variable had many bad values (US mainland cities, garbled
encodings, mixed capitalization). Rewrote `standardize_municipio` to:
- **Strip accents/tildes FIRST** (á→a, é→e, í→i, ó→o, ú→u, ñ→n, plus garbled
  PDF-extraction chars like Ă, ą, soft-hyphen) — must happen *before* `upper()`.
- **Convert to UPPERCASE** to eliminate case-sensitivity issues.
- Strip suffixes ("PUERTO RICO", "P.R.", "PR", "USA", etc.).
- Fix typos and map barrios/neighborhoods to municipalities
  (SANTURCE→SAN JUAN, PALMAS DEL MAR→HUMACAO, etc.).
- Added `validate_pr_municipio` — checks against the 78 valid PR municipalities
  (UPPERCASE list).
- **Multi-source fallback:** if `county` isn't a valid PR municipality, try
  `real_estate_municipality`, then `mailing_county`, before dropping. Do NOT
  simply drop US-location records — the real municipality is often in another var.
- Flagged confirmed US mainland cities (AUSTIN, BOCA RATON, BOYNTON BEACH,
  DURANGO CO, etc.) as empty so fallback/drop logic handles them.

Specific late fixes: AAąASCO→ANASCO, RA­O GRANDE→RIO GRANDE, RINCANN→RINCON.

### 2. Duplicate Filenames Across Source Files
Same record can appear in multiple source files. Added dedup on `filename` after
combining the 2019+ files, and before any `merge 1:1`.

### 3. CRITICAL FIX — ID Chaining Was Broken
**Symptom:** Nearly every person showed only 2 years of data, even though they
clearly filed in more years. Matching appeared to "stop after the first match."

**Root cause:** Stata's `merge` does NOT overwrite an existing variable. The
master (`all_2019plus_records.dta`) had `id = ""` for every record, so merging in
the matched IDs left `id` empty — matched records never inherited the base ID,
so the chain couldn't propagate forward.

**Fix:** `drop id` from the master BEFORE the merge, so the ID comes in from the
matched-IDs file. Then handle unmatched records (`id = filename` to start a new
chain). This applies to ALL reporters, not just 2015-2018 ones — a person first
seen in 2019 gets `id = filename` and future years chain onto that.

Result: chains now extend across all years; match rate ~63%.

### 4. Invalid `report_year` Cleanup
Values like `2` and `7000` are extraction errors. After combining 2019+ files,
records with `report_year < 2010 | > 2025` are reassigned by source file
(2022 batch → 2021, 2023 batch → 2022) and dropped if still unfixable. Bad
`match_year` values set to missing. **Ran cleanly this session.**
